# Decker — CLAUDE.md

## Project overview

**Decker** is a Linux application for Elgato Stream Deck hardware. The architecture has three components in the same repo:

- **Server monitor** (`src/decker/server/monitor.py`) — the process launched by `poe server`. Starts the server subprocess, then polls it continuously for health (RPyC heartbeat) and memory usage. If the server fails to respond or exceeds the memory limit (1 GiB), the monitor stops it and restarts it automatically.
- **Server** (`src/decker/server/`) — handles hardware communication via `python-elgato-streamdeck`. Runs **headlessly** as a separate subprocess (RPyC on port 18861), supports multiple simultaneous clients. Started and supervised exclusively by the server monitor. Exposed RPC commands are discoverable through `commands` (devices, pages, keys, plugins, icon packs, settings, `heartbeat`, `status`, `stop`). There is no `start` RPC — the server is already running when clients connect. Key faces may be animated GIFs, played by a per-device adaptive writer in `src/decker/animation/` (see `docs/superpowers/specs/2026-11-17-animated-key-faces-design.md`).
- **Client / UI** (`src/decker/client/`) — a PyQt6 GUI built on a `QStackedWidget` view system. `MainWindow` (`window.py`) registers its views (`DashboardView`, `DeviceView`, `ErrorView`, plus the `ReconnectWaitingOverlay` shown while disconnected) keyed by `ViewName(StrEnum)` and is the sole writer to the `AppContext` singleton. Settings live in a separate non-modal `SettingsDialog` (`widgets/settings_dialog.py`). `ConnectionManager` owns the RPyC connection on a background thread (no Qt imports) and pushes `AppEvent`s (`ServerConnectedEvent`, `ServerDisconnectedEvent`, `DeviceListUpdatedEvent`, `KeyEvent`) through a thread-safe `EventHub`, which `MainWindow` drains on a 16 ms `QTimer` and routes to the active view.
- **Plugins** (`src/decker/plugin/`, `src/decker/server/plugins.py`, `decker_plugin_sdk`) — actions and icon packs come from installed plugins, never from server code. Decker ships one built-in static plugin, Blank (`src/decker/builtin_plugins/`; it cannot be uninstalled), and nothing else (Counter comes from the default repository). Manifest actions may be `"static"` presets with no process; text fields may opt in to `{page_name}`/`{page_index}`/`{page_count}`/`{current_profile}`/`{profile_id}` templates (`template: true`), `page` and `profile` settings types are resolved by the server, and plugins switch pages and profiles with `switch_page`/`switch_profile`. Each plugin runs **out of process** (one child per plugin, JSON over stdin/stdout) and is supervised with restart and a watchdog; a crashing plugin cannot take the server down. Plugins are written against the `decker_plugin_sdk` package and shipped as `.deckerplugin` packages whose `manifest.json` declares `format: 1` and `contributes` (`actions`, `icon_packs`). Each plugin gets its own uv environment. Settings forms are generated by the client from the manifest's schemas, and Decker draws the key background and title (users can also set a per-key `icon` appearance override, which replaces whatever the action or plugin would show on the key (Clear icon restores it); the editor's live preview comes from the `key_preview` RPC, which composes a draft without saving); plugins supply the key image via `set_image` and may supply a fallback title via `set_title`. The `plugin_install`/`plugin_uninstall` RPCs, and `icon_import` (which adds to the `decker.user` User icon pack), are restricted to loopback clients unless `server.allow_remote_plugin_install` is set. Icon packs are served over RPC (`iconpacks_list`, `iconpack_icons`, `iconpack_icon`); the client picker browses them remotely and reads no local pack folders. Decker also serves the server's freedesktop icon theme as ten virtual packs `decker.system.<category>` (Actions, Applications, Categories, Devices, Emblems, Emotes, Mimetypes, Places, Status, Other; `src/decker/asset/systemicons.py`), shown as "System Icons" in the library (Linux-only: hidden on Windows and macOS); the theme is `icons.system_theme` or the desktop's current one, and the `decker.system.` pack id prefix is reserved. Key fonts resolve via `fc-match`, then an index of the OS font folders, then the bundled DejaVu Sans, and the client registers the bundled fonts with Qt. The monitor sets a stop event so the server's normal shutdown, including stopping plugin processes, runs on every OS; plugins rely on stdin EOF only if the `terminate()`/`kill()` fallback is reached on Windows (where terminate is a hard kill); Windows has no process-group semantics here, so helpers left by an executable plugin after its leader exits are not cleaned up (follow-up: Job Objects with `KILL_ON_JOB_CLOSE`). See `docs/platform-support.md`. Plugin repositories (JSON index format v1, `plugin.repositories` / `plugin.update_check` config) are fetched, cached under `~/.decker/repositories/` and checked for updates by the server (`src/decker/plugin/repository_index.py`, `server/repositories.py`, `server/update_checker.py`); `repositories_check` runs in the background and ends with the `repositories_check_finished` event (network fetches never hold the store lock and have total deadlines); the server pushes `plugin_updates_available` and installs from a repository through the normal installer (`plugin_install_from_repository`). Adding/removing repositories, changing the schedule and installing from a repository are loopback-gated like `plugin_install`. See `docs/plugins/repositories.md`.
- **CLI client** (`src/decker/cli/`) — a terminal client (`poe cli <command>`) that introspects the server's live RPC surface via `commands()` — no hardcoded command list.

Early alpha; the hardware integration layer and server/client separation are the current focus.

## Server fault-tolerance model

`poe server` launches the **server monitor**, not the server directly. The monitor:

1. Spawns the server as a child process.
2. Periodically sends an RPyC heartbeat; a non-response counts as a failed check.
3. Periodically samples the server process's RSS memory via `psutil` (`decker.common.processes.rss_bytes`).
4. If consecutive failed heartbeats reach the threshold **or** RSS exceeds **1 GiB**, the monitor stops the child and restarts it. Stopping asks the server to shut down (a shared stop event, so the normal shutdown runs on every OS), waits `server.stop_timeout` seconds (default 10), then terminates and finally kills it.
5. If the server exits with **code 0** (triggered by the `stop` RPC), the monitor treats it as an intentional shutdown and exits cleanly — it does **not** restart. Any non-zero exit code is treated as a crash and triggers a restart.
6. If starting the new child fails, the restart is retried on the next check round; there is no backoff or maximum restart count yet.

The server itself has no self-healing logic — fault tolerance is entirely the monitor's responsibility.

## Running the project

```bash
# Run the server (normal mode)
poe server

# Run the GUI client
poe client

# Run the CLI client
poe cli list            # list all server commands
poe cli status          # call a specific command
poe cli stop            # gracefully stop the server (monitor exits too)
```

System dependencies required: `libhidapi` (`sudo pacman -S hidapi` on Arch/Manjaro) and `uv` (builds per-plugin environments). Plugin author docs live in `docs/plugins/`; keep them in sync with protocol and manifest changes.

## Code style

- **Formatter**: black (line length 120) + isort (`black` profile). Let the formatter decide; don't fight it.
- **Types**: Always annotate — return types, parameters, and instance attributes — even when mypy doesn't require it.
- **Naming**: `snake_case` for functions/methods/variables/modules, `PascalCase` for classes, `UPPER_CASE` for module-level constants.
- **Docstrings**: Public classes and public functions only. One short line is enough unless the contract is non-obvious. No multi-paragraph docstrings. Private/internal members (`_` prefix) get no docstrings.
- **Comments**: Only when the *why* is non-obvious. Never narrate what the code already says.
- **Method size**: Keep methods under 50 lines. If a method is growing, extract a private helper rather than commenting sections.
- **Max args**: 5 per function/method (pylint enforces this).

## Testing

- Framework: `pytest` with `assertpy` for assertions.
- Target: **≥ 85% coverage** (`poetry run poe test` reports this).
- Test files live in `tests/` mirroring the source layout.
- Pylint docstring requirements are relaxed in tests (configured in `pyproject.toml`).
- Do not mock the database or other infrastructure unless absolutely necessary — prefer integration-style tests against real components.

## Architecture constraints

- `poe server` launches the monitor, which launches the server — never start the server directly in production.
- The server runs headlessly; it has no GUI of its own. `application.py` exists for potential future use but is not loaded server-side.
- Do not add a `start` RPC to `DeckerService` — the server is already running when clients connect.
- `stop` RPC exits the server with code 0; the monitor interprets code 0 as intentional and stops itself. Never restart on code 0.
- Server and client are separate entry points; keep their modules decoupled.
- Server must support multiple simultaneous clients.
- All hardware interaction goes through the server; the client never talks to hardware directly.
- Fault-tolerance (restart, health checking, memory limiting) lives in the monitor, not in the server.
- Process groups, tree termination and RSS reading are cross-platform and live in `decker.common.processes` (the Windows tree kill is psutil-based and leaves orphans of an exited leader alone, since pids are recycled; POSIX uses `os.killpg`); use it instead of `os.killpg`, `start_new_session` or `/proc`.
- Each device has profiles (integer ids, lowest unused first, reused after deletion; id 0 is "Default"), and each profile owns its pages. Key assignments, key images and labels are stored per page (`PageStore`, `pages.py`; page ids are unique per device, so a page identifies its profile). Each device shows one active profile and page; only that page's actions are live, and `PageController` (`page_controller.py`) owns every page and profile switch. Key RPCs take a `page_id`. `key_move`/`key_copy` re-key or copy a key's assignment within a page (a move keeps the instance's context id; a copy gets a new one). In the client grid a click selects a key for editing, its hover play-circle icon runs it (click = press, hold = long press), and dragging a key onto another moves it (Ctrl: copies it).
- Device IDs are stable 8-char CRC-32 hex strings derived from the device serial number. The selected device is persisted as `client.default_device` in the user config layer.
- Configuration is YAML-based; use `flatten-dict` for nested config operations.
- RPyC is the IPC layer between server and client.

## Platform support

Five tiers, in priority order: (1) Linux Arch/Manjaro/Plasma/Wayland, (2) Linux Ubuntu/Debian/Fedora/GNOME, (3) Linux other (90-100%), (4) Windows (75%+), (5) macOS (75%+). Every feature and plugin must target them. Update `docs/platform-support.md` (and the plugins repo's table) in the same change; plugins declare `platforms`/`linux` in the manifest.
