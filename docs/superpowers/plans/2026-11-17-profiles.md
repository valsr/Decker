# Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-device profiles (named, switchable sets of pages) with a client dropdown and edit dialog, `profile` plugin settings and `switch_profile`, new variables, and a Profile Navigation plugin.

**Architecture:** A `profiles` table plus a `profile_id` column on pages, inside `PageStore` (page ids stay unique per device, so key assignments, device state and stored `page` settings are untouched). `PageController` gains profile switching/clone/delete on top of the existing page switch. Plugins reach profiles through a resolved `profile` settings type, a `profile_field` on `page`, and `switch_profile`/cross-profile `switch_page`. The client adds a `ProfileSelector` and `ProfileEditDialog`.

**Tech Stack:** Python 3.14, SQLite, PyQt6, RPyC, pytest + assertpy (offscreen Qt), poetry/poe gates.

**Spec:** `docs/superpowers/specs/2026-11-17-profiles-design.md`

## Global Constraints

- Gates after every task: `poe format`, `poe mypy`, `poe pylint` (>= 9.0), `poe test` (coverage >= 85%). Run the tasks' tests first; the full suite at task end.
- Profile ids: **integers per device, lowest unused id starting at 0**, reused after deletion; dropdown order is `position` (append on add), never id order. First profile: id `0`, name `Default`; new profiles `Profile <id>`; new profile gets one page `Page 1`.
- Stored `profile` setting value: `""` (follow the current profile) or the decimal string of the id (`"0"`, `"1"`). Resolved value delivered to plugins: `{"profile_id": int, "name": str, "index": int, "icon": str}`; unset/deleted: `{"profile_id": -1, "name": "", "index": 0, "icon": ""}`. `index` is the 1-based dropdown position. (For `""` the resolved value is the current profile.)
- Resolved `page` value gains `profile_id` (`-1` when empty). `page` ids stay opaque strings; page ids identify their profile.
- `{current_profile}` = profile name, `{profile_id}` = the integer id as text.
- Profile icon: an icon ref string; `""` means the Decker icon, whose built-in ref is `DECKER_ICON_REF = "decker:logo"` (served from `src/decker/assets/decker.svg`). Delivered/resolved icons always carry a non-empty ref.
- Lock order of the page switch is kept: no controller lock is taken from hardware/plugin paths that hold their own locks (`active_page_id` stays lock-free once recorded).
- Last profile of a device cannot be deleted; blank profile names are rejected; deleting the active profile switches to the next (else previous) profile first.
- Invariant: the active page of a device is always a page of its active profile.
- Decker becomes **0.5.0** (`pyproject.toml`, manifests/pins in `decker-plugins`).
- Commit trailers: `Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>` and `Claude-Session: https://claude.ai/code/session_01FG9NRh1jMLQUSqz1T3VCXN`. Explicit-path `git add`. Never push or open PRs without the user's go-ahead.

## Review Focus

- Upgrading a database that has pages, page defaults and keys (and one that predates pages): everything lands in profile `0` `Default`, the default page is kept, a second `create()` changes nothing.
- Id reuse: delete profile `1`, add one; a stored `profile` setting `"1"` now resolves to the new profile (name shown is the new one), never crashes.
- Deleting or switching away from the active profile while its page's actions are live: the old actions are deactivated, the new profile's default page shown, no stale `_active` page (invariant above).
- Clone isolation: copied keys have new context ids; editing/deleting the clone's keys or pages never touches the original; cached key images/labels are copied.
- A plugin `switch_page` to a page in another profile, and `switch_profile` with garbage (`profile_id` as a string/None/unknown, `to` unknown, single profile) is ignored without raising; no deadlock with `refresh_page_dependent`.
